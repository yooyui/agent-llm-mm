# 进度追踪对照表

## 目的

本表用于把“原始规划 / 当前实现 / 剩余缺口 / 下一步任务”放到同一处，方便后续开发时持续更新，而不是每次都在多份历史文档之间来回比对。

当前追踪基线：`2026-05-09`

建议把它当成“任务推进总表”使用：

- 每次完成一个任务后，至少更新对应行的“当前状态 / 当前证据 / 剩余缺口 / 建议下一步”
- 如果某项范围被 roadmap 调整，再同步更新“目标态”
- 若有 fresh 验证结果，优先写入具体命令、测试集或 `doctor` 输出，而不是只写“已验证”

## 状态标签

| 标签 | 含义 |
| --- | --- |
| `已完成` | 当前阶段承诺已落地，并且已有文档或测试支撑 |
| `部分完成` | 已有可用 MVP 或局部实现，但离目标态仍有明确差距 |
| `已规划` | 已进入后续规划并有明确路线图，但尚未完成对应产品实现 |
| `未实现` | 目标已被讨论或列入路线图，但仓库里尚未形成可用实现 |
| `暂不纳入近期承诺` | 方向存在，但 roadmap 明确不作为近期交付目标 |

## 产品化二次跟进落地清单

本轮 P1/P2/P3 本地可核验切片包括：

- product readiness checker、source-only release decision artifact、plan/reality sync、structured blockers
- decision protocol v2 metadata、evidence relation read model、episode summary projection、read-only layered memory projection
- provider readiness diagnostics、remote/team read-only inventory、security/auth gate contracts
- `doctor.system_layer_report` 只读架构分层报告、`evidence_relation_contract`、substrate diagnostics、physics principle mappings、dependency rules、Phase 0-8 coverage 和 non-claims
- product wording guard，阻断 Beta、GA、production-ready、remote/team、remote write admin、complete self-governance、Local Alpha complete、multi-tenancy、all-entry automatic self-reflection、`run_reflection` 替换、provider gateway、write-capable daemon、physics runtime / solver / controller / scientific validation 等缺少 gate 的措辞
- observe-only daemon diagnostics、support bundle provider payload hardening、source-only release boundary artifacts

这些切片不改变以下 blocker：真实 fresh-machine、Windows runner、installer packaging、人工 approved release decision、remote/team 产品实现、auth/authz/audit/rate-limit/tenant/rollback、daemon writes、完整 memory architecture、physics-informed runtime。

## 维护建议

- 如果某个任务只是补测试或补文档，也应同步更新对应行的”当前证据”
- 如果某项能力从 `部分完成` 进入 `已完成`，最好附上最新验证命令或测试集名称
- 如果 roadmap 改了优先级，不要只改 `roadmap.md`，也要同步改这里的”建议下一步”
