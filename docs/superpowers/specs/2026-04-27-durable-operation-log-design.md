# Durable Operation Log Design

## Purpose

Replace the ephemeral in-memory `OperationRecorder` (bounded VecDeque, lost on process exit) with a persistent SQLite-backed operation log. This is a prerequisite for background daemon mode and remote management — both require durable audit trail of what the agent did and why.

## What Counts as an Operation Event

Any discrete action the agent performs or receives:
- MCP tool invocations (start + completion)
- Auto-reflection triggers and outcomes
- Model decisions
- Snapshot reads
- Doctor diagnostics
- Errors

## Difference from In-Memory Recorder

| Aspect | In-Memory Recorder | Durable Operation Log |
|--------|-------------------|----------------------|
| Lifetime | Process-scoped | Persists across restarts |
| Storage | VecDeque (bounded, ~256 entries) | SQLite table (retention-managed) |
| Purpose | Real-time SSE/broadcast to dashboard | Audit trail, diagnostics, correlation |
| Write path | Direct append | Insert via `OperationLogStore` port |

The in-memory recorder continues to serve real-time subscriptions. The durable log is a parallel write path for persistence.

## Minimum Schema

```sql
CREATE TABLE IF NOT EXISTS operation_log (
    operation_id TEXT PRIMARY KEY,
    occurred_at TEXT NOT NULL,
    namespace TEXT,
    actor_kind TEXT NOT NULL,
    actor_id TEXT NOT NULL,
    entrypoint TEXT NOT NULL,
    operation_kind TEXT NOT NULL,
    status TEXT NOT NULL,
    correlation_id TEXT,
    request_summary_json TEXT,
    response_summary_json TEXT,
    diagnostic_summary_json TEXT,
    redaction_version INTEGER NOT NULL DEFAULT 1
)
```

## Retention Policy

- Default: no automatic deletion (local-only, disk is cheap)
- Future: configurable max-age or max-rows via config file
- Explicit `VACUUM` left to user/daemon

## Redaction Requirements

- API keys, secrets, and bearer tokens must be scrubbed before insertion
- `redaction_version` tracks the scrubbing algorithm version (allows re-scrub on upgrade)
- Redaction happens at write time in the domain layer, not in the store

## Correlation ID

- Optional field linking related operations (e.g., tool-start → tool-complete, trigger → reflection)
- Generated by the caller, not the store
- Enables "show me everything that happened during this reflection cycle"

## Local-Only Default

- Operation log writes to the same SQLite database as events/claims
- No network export in this phase
- Dashboard reads from operation log for historical view (read-only)

## Acceptance Tests

1. Operation log records a tool start and completion (insert + query)
2. Operation log redacts secrets from model/provider config in summary JSON
3. Operation log links auto-reflection diagnostics by correlation id (query by correlation_id)
4. Operation log can be queried by namespace and time range
5. Operation log write failure does not corrupt MCP stdout
